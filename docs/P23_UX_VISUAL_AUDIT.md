### Observed architectural pattern

- Desktop sidebar renders **17 keys across six groups**; mobile bottom navigation renders five (`overview`, `activity`, `scan`, `budget`, `insights`). Secondary mobile destinations depend on indirect page links. **C**
- Each screen is imported statically by `FinanceApp.tsx` and included in an inline conditional router. **C**
- Navigation from AppShell calls `history.replaceState`; page-local `navigate()` updates React state only. Consequently in-page route changes do not consistently update URL/history. **C**
- The same presentation patterns (Surface cards, Badge, page headings, analytic dashboards) are used nearly everywhere. **C**
- Accounts/net-worth, Budget/goals and Insights/categories are alternate views of one underlying component. **C**

## 4. Baseline visual design, source-confirmed

| Property | Current implementation | Audit interpretation |
| --- | --- | --- |
| Palette | Light grey `#f5f6f8`, white surfaces; dark `#0d1015`, `#151920`; violet accents | Coherent but visually generic and close to developer-dashboard styling |
| Typography | Inter/system stack; tabular numerals on money | Sound arithmetic readability basis; insufficiently strong information-density hierarchy |
| Surfaces | All `.f-surface` use 16px radius, stroke, shadow and 20px padding | Card proliferation; too much container chrome for routine finance |
| Headings | Home H1 up to 40px; many route headings 25–40px | Page copy takes space that should display balances and actions |
| Layout | 248px fixed desktop sidebar, 64px topbar, 74px mobile bar | Clear scaffold, excessive permanent destinations on desktop |
| Charts | Recharts, custom palette and grid; chart/table components | Useful functional base; needs explainable scales, linked selections and visual standardization |
| Motion | 120/180ms tokens, transitions in buttons/nav | Restraint is good; interaction animation lacks semantic consistency |
| Mobile | Bottom navigation and responsive CSS breakpoints | Mobile layout implemented but touch ergonomics and real devices not qualified |
| Error/empty | Auth/unconfigured/error variants in domain pages | Inconsistent recovery actions; some paths end in explanatory dead-ends |

**No overall numeric visual score is asserted.** A defensible quality score requires actual light/dark screenshots with both populated and unpopulated states and reviewers evaluating the same rubric.

### Required P25 visual quality direction (not a locked design)

A premium **Ledger Studio** experience: restrained color and low ornament; compact, precise finance hierarchy; dense financial tables with progressive disclosure; calm, meaningful motion; purpose-built mobile capture and review; avoid decorative hero statements, feature-phase badges, "SaaS card walls" and chat-first AI framing.

## 5. Critical user journeys to measure

| Journey | Success definition | Known/source-observed friction |
| --- | --- | --- |
| Open app after sign-out | See clear sign-in entrypoint, recover original route | Overview unauth message is not actionable |
| Create expense | Select account, split category if necessary, validate, review, submit | One-category, EUR-only form |
| Find old purchase | Search item/merchant/date, open supporting evidence, navigate Back | Search promise, hash state mismatch |
| Review receipt | Capture, inspect image, correct OCR, link to one or more transactions | Capture lacks preview; review elsewhere |
| Import bank statement | Map, dedupe, review, commit, reconcile | Exists as backend/UI; end-to-end timing U |
| Budget an upcoming payment | Identify recurring commitment, reserve allocation, inspect remaining | Requires crossing Recurring/Plan/Home |
| Compare merchants | Filter category, inspect prices and underlying purchases | Insights/Products/Merchants fragmented |
| Account session restoration | Google/email sign-in returns to requested screen | OAuth path requires real-account U |
| Mobile one-handed entry | Scan and post expense without clipped controls | Screenshot/touch testing U |
| Accessibility | All core actions keyboard/screen-reader operable; important writes reversible/validated/confirmed | Needs interactive authenticated testing U |

Human timing and task-success studies: at least five representative participants, each completing the same script unaided; record task success, time, errors and subjective workload. Do not infer scores from repository code.

## 7. P24 handoff — decisions to lock

1. **Primary user task model:** Home (position), Activity (record/find), Plan (allocate), Explore (understand), Receipts (capture/reconcile), Wealth (accounts), with Settings/support secondary.
2. **Source of truth for routes:** one central router and history model; all `onNavigate` consumers use it; tests for direct linking, Back/Forward, refresh and hash query params.
3. **No hero:** utility first on Home; display balance and actionable work before explanatory paragraphs.
4. **Progressive density:** finance tables on desktop, legible rows and accessible detail screens on mobile; avoid converting table rows into unstructured cards.
5. **Native-first scanner:** previews, capture state, OCR evidence, edit/correct/match, explicit failure recovery.
6. **Preserve integrity:** ledger remains authoritative; receipts and valuations never silently become posted transactions.
7. **Design 3 truly different directions in P25**, compare with real-device screenshots; lock selected reference with a scored rubric before P26 implementation.
8. **Release gates:** no P24 signoff until anonymous screenshots are reviewed, auth/fixture capture is scheduled, task criteria defined, and known P1 defects have owners.
